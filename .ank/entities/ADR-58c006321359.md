GitHub publishes `<asset>.sha256` beside every Brave asset, and `nix-prefetch-url` computes the
hash we pin. Nix only verifies the hash it is handed, so a checksum fetched over the same channel
as the artifact proves nothing on its own: TOFU was still the whole trust story. Signature
verification makes the published checksum meaningful — we fetch `<asset>.sha256.asc` and check it
before the checksum can gate a pin.

The key is vendored in the feature directory, not fetched. Fetching `github-checksums-release.asc`
would trust the same S3 bucket the checksum came from, which is TOFU again with extra steps. The
fingerprints live in metadata.json so a silent Brave key rotation fails loudly: `tests/updater.bats`
extracts the fingerprints of `features/hm-brave/checksums-key.asc` with real gpg and compares them
to what metadata.json pins. Updating the key is then a deliberate diff: drop the .asc in, edit the
fingerprints, and the test decides whether it is right.

`sigKey` also carries the channel. Brave's beta and nightly checksums are signed by separate keys,
`github-checksums-beta-release.asc` and `github-checksums-pre-release.asc`, so a signature that does
not verify against the vendored release key is a pre-release asset — the check enforces the channel
without depending on GitHub's `prerelease` flag, which is false for beta and nightly because they
ship from other stable branches. `channel` is a jq expression over one release object and selects
which releases are discovered at all; brave pins `.name | startswith("Release ")`. Default discovery
is unchanged for features without a channel, so tmux, ts and the rest keep their behaviour.

Measured on the live tree: stable `v1.98.63` and `v1.99.55` verify against the vendored ring
(10A714…, 7FE68A…, B84010… — the ring holds three Brave public keys), and `update.sh --check` now
reports `1.99.54 -> 1.99.55` instead of nightly `v1.101.32`, which GitHub's `releases/latest`
endpoint happily returned before discovery was channel-filtered.
