Pi-Bolt ships the CLI as tag releases named `bolt-v<version>`; the `android-v*` and `ios-v*` tags
are companion releases that carry a prebuilt `cli.ts` and no linux asset. The release page gives an
install script that unpacks the asset into `~/.local/share/pi-bolt/versions/<ver>/bin/` and installs
pnpm there; none of that belongs in this flake (ADR-3611: nothing installs into the home directory,
updates go through the pin). features/hm-pibolt/metadata.json pins the asset with `kind = "sri"`
(ADR-8b56), `strategy = "latest"` with the channel filter keeping only `bolt-*` tags, and
`pinMeta.systems = ["x86_64-linux"]`, because every host here is that architecture. The release
carries the asset beside `-jit`, `-baseline` and `-musl` variants and darwin/win32 ones, so the pin
names exactly one file, `pi-bolt-linux-x64.tar.xz`, and the `pi-bolt-kit-*`/`pi-bolt-runtime-*`
assets belong to other install routes, not to this package.

`version` is the tag, `bolt-v1.3.0`, not a semantic version: pin-meta is a shape contract for the
two expanders (ADR-0b73), not a semver check, and the tag is what the download URL names
(`/releases/download/bolt-v1.3.0/pi-bolt-linux-x64.tar.xz`). A leading `v` is stripped by the
updater and this tag has none, so `{version}` expands to the tag verbatim. The tarball holds one
directory, `pi-bolt-linux-x64/`.

The layout is the whole decision. `pi` is a single-file Bun binary that reads its version stamp from
`package.json` resolved beside the executable it actually resolved, `dlopen`s `native/*.node`
relative to that same file, and takes its settings from `pi-settings/`, themes from `theme/` and
examples from `examples/`, all sitting beside it. So the extracted tree moves to
`$out/libexec/pi-bolt` as-is and `$out/bin` holds only two symlinks into it. Moving one file,
copying the tree, or naming the directory anything else yields `pi --version` printing 0.0.0 or a
binary that cannot load its native modules, so features/hm-pibolt/_package.nix asserts both from
the store path in its own installCheckPhase: `pi --version` must not be 0.0.0, and `pi-start --help`
must name pi-bolt. pi needs the interpreter and rpath rewritten into the store; pi-start is
statically linked and needs nothing. The asset is an opaque vendor payload, so doStrip is off and
the tree is not filtered, which is why the store path is about 240MB — the payload carries nested
`node_modules` copies, and features/hm-pibolt/_package.nix's shortcut records what upgrades it.

`home.packages` rather than a `programs.*` module: Home Manager declares no `programs.pi`, and a
program module would install one package while hiding `pi-start`, the detached launcher upstream
documents for shells whose PATH is slow to resolve. `meta.mainProgram = "pi"` says which of the two
names is the program (ADR-380b: the package travels through the package set, reached by
callPackage, not an overlay). features/hm-pibolt/update.sh is the lib/updater.sh symlink whose URL
expansion is byte-compared with lib/pin-meta.nix by the gate (ADR-122a). Upstream's `pi-bolt update`
and its `npx`/install.sh routes are not used; a bump is a pin change.

Two limits the ADR records rather than fixes. The release also carries `SHA256SUMS`, signed, as a
manifest over every asset in it, including the darwin and win32 ones; Nix verifies the SRI in
metadata.json at fetch, so the manifest is not parsed, and a tag that renames or re-builds the asset
fails the fetch rather than installing something else. And `pi` on PATH collides with hm-dev's
`pi-coding-agent` from pkgs.unstable (ADR-3611): Home Manager puts both on PATH and the later entry
wins, so a host listing both gets one of them and neither route updates the other. A host picks one.

Consequences: no host lists hm-pibolt today, so coverage is input-side (`tests/pins.nix` plus the
expander parity diff), eval-side through the fixture host in `tests/home.nix` that asks for it and
finds one unwrapped package carrying the pinned tag, and build-side through installCheckPhase when a
host actually builds it. mise or an npm install can still shadow `pi` in PATH, as with hm-ank; this
feature never deletes a file outside the store.
