nh is a second deploy client in `features/hm-njust/nix.just`, beside `nix build`,
`nixos-rebuild` and `home-manager switch`. It is a different shape of client, and
the file's existing conventions do not carry it:

- `_exec`'s `--dry-run` means "print it, run nothing". nh's own preview is `-n/--dry`
  ("only print actions, without performing them"), which evaluates for real and prints
  the plan. `_clean` already translates `--dry-run` to `--dry` for the same reason;
  the deploy recipes follow that precedent rather than `_exec`'s print-only branch.
- `_exec`'s `--sudo` prefix-wraps with `sudo env "PATH=..."` because sudo's `env_reset`
  drops Nix's bin dir. nh elevates inside itself (`-e/--elevation-strategy`, auto:
  doas/sudo/run0/pkexec), so a recipe that also wrapped sudo would elevate twice and
  put a sudo'd nh in front of a PATH nh does not inherit. `--sudo` is therefore dropped,
  not forwarded: `nh os` and `nh home` have no such flag.
- `_deploy` resolves the attribute itself (`#homeConfigurations.<user@host>.activationPackage`,
  `#nixosConfigurations.<host>.config.system.build.toplevel`) because `nix build` takes an
  attribute. nh takes an installable and resolves the attribute from its own flags
  (`-c/--configuration`, `-H/--hostname`), so a nh recipe names the flake root and the
  target and lets nh spell the attribute. That is why these recipes do not reuse `_deploy`.

Measured against nh 4.4.2 (`nh os --help`, `nh home --help`): `os` takes
switch/boot/test/build; `home` takes switch and build only; both take `-n/--dry`,
`-L/--print-build-logs` and `-v/--verbose`; `os` selects a host with `-H`, `home` a
configuration with `-c`.

The one thing nh does not guard is a remote home target: `nh home switch -c bob@otherhost`
builds another host's home config and activates it on this one, which is the hazard
`_deploy` already refuses for `hm`. That guard stays in njust, since nh has no notion of
which host the caller is on.
