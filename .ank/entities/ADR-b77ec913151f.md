disko's `gpt` content is safe on a disk it owns and unsafe on one it does not: for each partition
index it names it tries `sgdisk --new` first and, on failure, falls back to `--partition-guid`,
`--change-name` and `--typecode` on whatever already sits there. On a Windows disk that fallback
rewrites the GUID, name and type code of the partition Windows boots from — the data survives, the
boot metadata does not. ADR-eaca61b85782 therefore gates partitioning on `ownsWholeDisk`, and this
ADR settles what a `false` host does instead of being refused outright: methyl and propyl need
*some* disk management to deploy (an ESP to mount and a root filesystem to build into), so they get
terraform.sh.

What terraform.sh is allowed to do is the whole decision:

- read the table (`sfdisk --json`) and select two partitions: the one the host's mount point names
  when that name resolves on this machine, and failing that the ESP holding a `vfat` signature or an
  ESP type GUID, or the root holding the declared `fsType`. No other entry is touched. `wipefs`, `sgdisk --clear`, `sgdisk --new`, `--change-name`, `--typecode` and
  resizing are never run here: a partition this flake does not own is never a target, and the
  partition-table checksum taken before and after a run must be equal.
- `mkfs` only where `blkid -o value -s TYPE` returns nothing. A partition with a signature is
  adopted, whatever owns it. That is the rule that keeps a Windows or another Linux install alive.
- refuse rather than guess: no FAT ESP on the drive; an ESP whose signature is not `vfat`; a root
  partition whose signature is not the host's declared `fsType`; a blank target the host refers to
  by UUID (a fresh mkfs creates a UUID the generated hardware-configuration.nix cannot know).
- mount the declared root under `--root`, which is the precondition `deploy` already checks.

Gating is the same mechanism as install.sh's, not a second one: `confirm` asks one step at a time, a
run with no terminal is refused rather than assumed, and `--force` / `INSTALL_FORCE=1` is the testing
override. The mount is not destructive, so it is not prompted.

Proof is the disk-fixture tier, not a VM. Every tool terraform.sh calls takes a plain path and works
on a regular file, so the fixture hands it files (`<disk>p1` slices of a sparse image) and the script
never learns a fixture exists. That tier measures ~5s and ~80MB and asserts the thing the VM cannot:
that the MSR region, the NTFS region and a foreign `/EFI/systemd` loader are byte-identical after a
run. TASK-d365 is closed as superseded — `installTest` renumbers devices to `/dev/vda`, so it proves
layout and boot but never that a partition Windows owns survived.

Deferred, deliberately not implemented here: on a disk where another distro's systemd-boot already
occupies `/EFI/systemd`, writing our loader there clobbers it. The loader is written by the boot step
(`--install-bootloader`), not by terraform.sh, so the collision is a boot-step decision and is left
open until a shared Linux host is deployed for real.
