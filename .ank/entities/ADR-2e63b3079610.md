A `terraform.json` is generated from the drive by `terraform.sh --emit`, never assumed: it lists only
the partitions whose signature is a filesystem terraform.sh can reproduce, always says `owns: false`,
leaves out every partition it cannot reproduce and names each one on stderr, and prints the mounts it
cannot read off the drive as guesses a human must check before the recipe is used.

`--emit` is the only way a recipe is written, and it is read-only: stdout is JSON alone, so
`terraform.sh --emit --disk <drive> > hosts/<host>/terraform.json` is the whole workflow, and every
line that tells an operator what to change goes to stderr, where it cannot corrupt the file.

What it emits is the drive's own evidence, nothing more:

- `fs` from `blkid` and `size` from the partition table, exact, in the largest whole unit (G/M/K,
  otherwise bytes) so a size in the recipe never disagrees with the partition it describes.
- `label` from the filesystem, only when it has one. `name` is that label lowercased and sanitized;
  an unlabeled partition is named `esp` when it holds `vfat` and `p<N>` otherwise, because `name` is
  only the handle the plan prints and no device name depends on it.
- `mount` guessed: a `vfat` partition as `/boot`, the largest non-`vfat` filesystem as `/`, and
  announced as a guess, because a mount point is host config and no drive holds it.
- `owns: false`, always. Owning a whole drive is a decision a person writes; nothing on a disk says it.

What it refuses, with no JSON written at all:

- a drive with no partition table, and a drive whose table holds nothing reproducible. A recipe of
  partitions no filesystem was ever made for describes nothing, and the run that reads it would refuse
  anyway -- printing it would turn a refusal into a file someone later runs.
- more than one candidate disk: it names them and asks for `--disk` rather than choosing one silently,
  because picking a drive on a machine holding two is exactly the mistake this feature exists to avoid.
- `--emit` together with `--recipe`: one reads a recipe, the other writes one.

A partition that is blank is left out on purpose. It carries no intent: the drive cannot show what it
should hold, and emitting it with a guessed filesystem would produce a recipe that formats something
nobody asked for. It is named on stderr by its GPT partition name, so the operator declares the one
they actually want, and the recipe then identifies the drive by the fingerprints it really holds. That
is why an emitted recipe for a Windows drive is a starting point rather than a finished file: the ESP
comes out, the Linux partition is added by hand, and the run then adopts the ESP -- which needs no
filesystem label, since ADR-b77ec913151f lets the ESP be found by its `vfat` signature or GPT type.

Proof is the disk-fixture tier: stdout parses as JSON on its own; an emitted recipe round-trips
through `--recipe <file> --mount <dir>` and a run of it moves no byte on the image; a Windows drive
emits its ESP only and names what it left out; and the emitted recipe plus one declared root partition
formats the blank Linux partition while the MSR region, the NTFS region and `/EFI/Microsoft/BOOT` stay
byte-identical.
